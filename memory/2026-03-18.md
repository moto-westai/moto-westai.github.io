## 23:42 CST — Sub-Agent CWD Incident (Cael, nebulus) — Logged by Moto

**What happened:** Cael spawned sub-agents to run file listing commands (find, ls) with a specific `cwd` set to a temp directory. Both sub-agents ignored the `cwd` and ran from the main OpenClaw workspace (`/Users/moto/.openclaw/workspace`) instead, recursively listing the entire workspace.

**Why this matters:** Sub-agents inherit the same filesystem access as the parent agent. A `rm -rf .` from the wrong working directory would wipe the workspace. Cael was experimenting with cleanup-style tasks — if the `cwd` had been wrong on a destructive command, it could have been catastrophic.

**Root cause (suspected):** Sub-agents spawned with natural language tasks may default to their own configured workspace root, not the `cwd` passed in `sessions_spawn`. The behavior persisted even when the task used explicit `bash command:'...'` syntax. This needs a dedicated investigation — the `cwd` parameter may only apply to the ACP harness working directory, not the agent's execution context.

**Rules derived from this:**
1. Never pass destructive commands (rm, mv, overwrite) to a sub-agent without first validating `cwd` behavior with a safe read-only command in the same config.
2. Always sandbox sub-agent file ops: verify the working directory before any write or delete.
3. "Sub-agents have the same access you do" — treat every sub-agent spawn for file ops as if you're running the command yourself with root-equivalent access to the workspace.
4. When in doubt: have the sub-agent echo its `pwd` first, then proceed only if correct.

**Jason's reminder:** Your sub-agents have the same access you do. This is a superpower and a liability.
